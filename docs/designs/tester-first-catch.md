# Design: First catch in five minutes (tester onboarding)

## Problem Statement

The gate works in daily use, but a new tester can't feel it quickly. A GTM engineer who installs the plugin today needs about six steps (plugin install at local scope, setup preview and apply, own facts, a CRM connection by file or HubSpot key and owner id, a new session) before their agent is caught for the first time. Until a CRM is connected, the gate refuses every draft, so the first catch is behind setup that has nothing to do with it. Separately, a hiring manager skimming the repo meets a fictional pipeline demo and a long README before the strong idea.

## What Makes This Cool

Your own agent, writing to your own prospect, gets stopped for a number it can't back up, and then gets through once the sentence from the company's own page is recorded. None of the guardrail tools we looked at (HarnessGuard and GouvernAI for Claude Code, and the AI SDR guardrail guides from Apollo and others) check a draft's numbers against the company's own site when the draft is created. (Amended per D7.)

## Constraints

- Audiences: GTM engineers who already use Claude Code (testers), and hiring managers who skim for about two minutes and never install.
- Testers won't hand their real sent mail to an unfamiliar tool, even an open-source one. The first catch must use a draft they choose to write now.
- Public repo: no real prospects, contacts or CRM ids in docs, examples or recordings.
- Stdlib only; no new dependencies.

## Premises

1. A tester's "whoa" is their own agent, on their own prospect, refused for an unsourced number and then passed once it's sourced, in about five minutes.
2. The CRM connection and the safety net are what block that today, and neither is needed for the first catch.
3. A hiring manager should see GTM judgement first, then "agents can't lie or send here", proven by one real catch on the first screen.
4. The daily-use plumbing (og proposals, strict mode, allow list) stays out of a first-timer's way until they choose to make it daily-safe.

## Cross-Model Perspective

A fresh Claude subagent (Codex not installed) read a summary cold. Its strongest points:
- No-CRM mode must land first: today file mode refuses every draft when there is no CRM file (`gates/evidence.py`, `read_crm`).
- Its "coolest version" was an audit of the tester's recent sends. Rejected in session: testers won't expose recent sends to an unfamiliar repo; they choose what the tool sees.
- Borrow promptfoo's shape ("assertions over many outputs, one report") rather than the tool, if a batch check is ever wanted.

## Approaches Considered

### Approach A: Truth-only first catch (minimal)
A no-CRM mode plus a "your own prospect" path in the quickstart and a README reorder. Not chosen alone: the tester still has to read a doc to know what to do. Folded into B.

### Approach B: Two-stage guided start (chosen)
Approach A plus one skill, `/outbound-gates:start`, with two stages: catch, then make it daily-safe.

### Approach C: Paste one email
A checker for any pasted email with no hook. Rejected: it guesses which sentence on a page backs each number (false "not found" results hurt trust), while B has the agent write the draft and the gate verify an exact quote that was recorded from the page. B also leads straight into the live hook in stage 2; C has no path there.

## Recommended Approach

**Approach B.**

**Stage 1, catch (no CRM, no setup, nothing in Gmail):** the agent's own draft is refused by the gate's check and passes once the source is recorded. The live hook stopping a Gmail draft is the first thing stage 2 shows.
1. The skill asks for one real prospect's email address. The company domain is the address's domain; the skill doesn't ask for it separately.
2. **Folder:** `start` runs only in a folder with no `.gates/`. If `.gates/` exists, it changes nothing and says "this folder is already set up: run /outbound-gates:status", or suggests a new empty folder for the try. It never rewrites an existing `config.json` or `style.json`. In a fresh folder it creates `.gates/` with `crm_source: "none"` and the neutral style, and says so.
3. The agent writes a short cold email to a file, using one number it believes about the company.
4. `og check` (or `python -m gates.evaluate` when the og launcher isn't installed yet) refuses it and names the number.
5. The agent finds the sentence on the company's own page and records it. If the page can't be read (for example a pricing page drawn by JavaScript), it says so plainly and suggests another page or dropping the number, never inventing a quote.
6. `og check` passes. The skill shows the before and after in five lines.

**Stage 2, make it daily-safe (offered, not forced):** connect the CRM (file or HubSpot), add own facts, install the safety net and optionally strict mode. Changes that loosen the gate go through `og propose` and the person's `og yes CODE`.

**No-CRM mode:** `crm_source: "none"` applies only to the command-line check (`gates.evaluate` / `og check`) and the source recorder (`gates.evidence record` / `og record`). There it checks rules, sources and calculations and skips the pre-send check, saying so in one line. **The Gmail hook never accepts "none":** in a "none" project it refuses every draft with "connect a CRM first (stage 2 of /outbound-gates:start)". Because the setting lives in the folder the agent writes to, it must not loosen the hook; switching a project that had a real CRM back to "none" therefore only stops its Gmail drafts, never lets more through.

**Recording a source with no CRM:** the allowed source hosts are the recipient address's domain and its subdomains (for example `www.` and `docs.`), plus the person's own `source_allowlist`. Today those hosts come from the CRM company's domain and alt domains; in "none" mode the address is the only evidence of who the company is.

**README, first screen:** one paragraph of GTM judgement (sourcing, qualifying, never emailing twice), then "agents can't lie or send here", then a 20-second clip of a real catch with every prospect detail replaced, then "Try it on your own prospect: /outbound-gates:start". The fictional pipeline demo moves below.

## Open Questions

- Later decision, not in this change: if testers ask for Gmail drafts before connecting a CRM, add a person-only `og propose` change recorded in the user's config (never the project folder) and applied by `og yes CODE`. Until then the hook refuses every draft in "none" mode.
- Recording the clip: a real catch from daily use, re-recorded on a fictional company, or the quickstart company? Real is stronger; fictional is safer for the public-repo rule.
- Does stage 1 need the og launcher? Before setup there is no `~/.config/outbound-gates/og`, so the skill must call the plugin's modules directly.

## Success Criteria

- A GTM engineer with Claude Code goes from plugin install to their own agent caught and passed in under five minutes, without opening a doc.
- Two of two testers reach the first catch without help when watched.
- A hiring manager who reads only the first screen can say what the project does and why it matters.
- Existing projects and daily use are unchanged; all current tests still pass.

## Distribution Plan

Ships in the plugin through the existing release workflow (tag `outbound-gates--vX.Y.Z`, zip on GitHub Releases, marketplace update). No new channel.
