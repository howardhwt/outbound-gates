## Problem Statement

outbound-gates checks AI-written cold email today, but only when a person or a skill remembers to run it. The goal is to turn the gates into something other GTM engineers' agents plug into: Claude via MCP now, Clay soon after. The gate has to stop a bad draft from being created at all, not just advise.

A second problem surfaced during the session. `check_claims` (`gates/checker.py:176-188`) accepts any claim with a value, a non-empty `url` and a valid date. Nothing checks that the page says the number. That was fine while a person reviewed the claim table. Once an agent calls the gate itself, the same agent writes the number and its "proof", and it can pass by pairing an invented number with any URL.

## What Makes This Cool

Every AI outbound gate found in the search judges *plausibility*, either with an LLM or with a human approve button. This one requires the draft to arrive with its proof, and the gate checks that proof itself. The verdict is a pure function: the same draft always gets the same verdict and names the exact rule that decided it. The pre-send half reads the real CRM (owner claimed, deal disqualified, unanswered contact), not the gate's own send log.

The demo moment, step by step against the components below:

1. The agent calls Gmail `create_draft` with a made-up "40%". The hook blocks it: `claims: the number '40%' has no sourced claim`.
2. The agent calls the `record_claim` tool with a URL that doesn't say 40%. The tool fetches the page and refuses: `record_claim: quote not found at URL`. Nothing is recorded.
3. If the agent instead writes a claim entry into the claims file by hand, the hook blocks the next `create_draft`: `claims_unverified: claim '40%' has no stored snapshot`.
4. The agent finds the real figure and calls `record_claim` with a URL and quote that contain it. The tool records it, the hook re-runs the gate, and the Gmail draft is created.

The GIF shows steps 1, 2 and 4. Step 3 is covered by tests.

## Constraints

- Audience: GTM engineers on GitHub and hiring managers reviewing it as a portfolio piece. The README and GIF are judged as much as the code.
- Claude / MCP first, Clay "very soon". The core can't live inside the MCP server.
- Standard library only, Python 3.9 to 3.14, CI offline (no live fetches in tests).
- Drafts only. A person sends every email, as the repo already promises.
- Must reuse the user's existing Gmail connector in Claude rather than add new Gmail auth.

## Premises

1. No model decides the verdict. The agent writes the draft and claims; the gate only checks them.
2. The gate sits in the path, not beside it. The draft cannot be created unless it passes.
3. One core, thin wrappers: one `evaluate()` returns one JSON verdict. MCP wraps it now, HTTP for Clay later.
4. One-line install, no new runtime dependencies.
5. (Revised after the second opinion) The gate verifies sources. The agent supplies a URL and a quote; the gate's own `record_claim` fetches the page, checks the quote is on it and the value is inside the quote, and stores a snapshot and hash. The verdict checks against stored snapshots, so it stays deterministic. The demo shows the gate catching a fake source, not just a missing one.

## Cross-Model Perspective

Independent cold read by a fresh Claude subagent (Codex not installed):

- **Coolest version:** make the claim file unfakeable. Add a `quote` field and have the gate fetch the URL, confirm the quote and value, and record a sha256 plus fetch time. That record doubles as the receipts page.
- **What excites the user:** "1 or 3". Both picks are versions where proof travels with the email.
- **50% already exists:** the official MCP Python SDK would cover transport, but conflicts with stdlib-only. Alternative: a small hand-rolled stdio JSON-RPC loop.
- **Challenged premise #5 (Critical):** "agent adds a source, it passes" shows the bypass, not the gate. Accepted; premise revised.
- **Where this doc departs from it:** it suggested fetching inside the verdict. Live pages change or block bots, which breaks determinism, so this design fetches once at `record_claim` time and the verdict reads the stored snapshot.

## Approaches Considered

- **A: Minimal, MCP server with two tools.** Rejected: an agent can skip `evaluate` and draft anyway, which breaks premise 2.
- **C: Receipts page first.** Rejected for now: needs hosting, makes prospect research public, and doesn't serve the "agents plug in" story. The stored snapshots keep this open for later.

## Recommended Approach

**B: verified evidence + a hook that blocks the draft.**

Components, all stdlib:

1. **`gates/evidence.py`**
   - `record_claim(domain, contact, url, quote, value)`:
     - Accepts `http` and `https` URLs only, and re-checks the scheme after every redirect (at most 5). It rejects `file://` and any other scheme, and any host that resolves to a loopback, private or link-local address.
     - Fetches with `urllib` (10 s timeout, 2 MB cap, plain User-Agent), reduces HTML to text, and confirms the normalised quote appears in the text.
     - Checks the value is in the quote. Both go through the existing `_normalise_number`, so "$1,200" in the draft matches "$1,200" or "1,200" in the quote. "12k" vs "12,000" is not equated.
     - On success, stores the page text at `<gates_home>/evidence/<sha256>.txt` and **appends** the claim entry (`claim`, `value`, `url`, `quote`, `evidence_sha256`, `fetched_at`, `checked`) to `<gates_home>/drafts/<domain>/<contact>/claims.json`. The tool writes this file itself, so the agent never has to.
     - On failure, returns the reason (`quote not found at URL`, `value not in quote`, `fetch failed: ...`, `scheme not allowed`) and writes nothing.
   - Claims are keyed per recipient (domain + contact address). Entries from earlier drafts to the same person stay, because each one is verified and can only allow its own number.
   - **One base directory for both processes.** The MCP server writes and the hook reads, and Claude Code launches them separately. Both call one function, `gates/paths.py:gates_home()`, which resolves in this order:
     1. the `GATES_HOME` environment variable
     2. `$CLAUDE_PROJECT_DIR/.gates`
     3. `./.gates`
     
     `.mcp.json` sets `GATES_HOME` to `${CLAUDE_PROJECT_DIR}/.gates` for the server, so both land in the user's project, never in the plugin directory.
   - **Path segments** come from the same module's `draft_dir(domain, contact)`:
     - the domain goes through the existing `normalise_domain`
     - the contact is lower-cased, and every character outside `[a-z0-9._@+-]` becomes `_`
     
     A test checks that the server and the hook build the same path for mixed-case and odd-character addresses.
   - `verify_claim(claim, store)`: offline. Confirms the snapshot file exists, its sha256 matches `evidence_sha256`, the quote is in it, and the value is in the quote.
2. **`checker.check_claims`:** a new rule, `claims_unverified`, runs when `require_evidence` is on.
   - A claim that fails `verify_claim` produces a FAIL and doesn't count as sourced.
   - A claim's `derived` values count only when that parent claim verifies. So an invented derived "80%" hung off an unverified claim still fails `claims`.
   - `own_facts` from config stay exempt (they are your own product facts).
   - `require_evidence` is off by default in `config.example.json`, so the existing demo and CLI keep working. The hook forces it on (see 5).
3. **`gates/evaluate.py`:** `evaluate(subject, body, claims, crm, *, domain, contact, register, today, sender_owner, max_unanswered, config, evidence_dir) -> dict`.
   - Runs the full `checker.check()` on the body only, exactly as the CLI does. It runs the subject-only subset (`claims`, `claims_unverified`, `dashes`, `banned_phrase`, `cost_assertion`, `bold`) on the subject, merges those findings with a `subject:` prefix, and runs `presend.presend_check()` on the CRM data. The split lives here, so the MCP `evaluate` tool and the hook give the same verdict.
   - Every input is explicit, `today` included. Nothing reads the clock or the network inside `evaluate`.
   - Output: `{"pass": bool, "findings": [{"rule", "level", "message"}], "inputs_sha256": "..."}`. The hash covers every argument. Same inputs, same bytes out.
4. **`gates/mcp_server.py`:** a hand-rolled MCP stdio server (JSON-RPC 2.0: `initialize`, `tools/list`, `tools/call`). Tools: `record_claim` and `evaluate`.
5. **`hooks/gate_gmail.py`:** a Claude Code PreToolUse hook.
   - **Tools it matches** (Gmail connector):
     - `create_draft` and `update_draft` are gated: the draft is created or changed only if `evaluate` passes.
     - `send_message`, `reply` and `forward` are always blocked. Drafts only; a person sends from Gmail.
   - **Fields gated:** the subject and the body. An HTML body goes through the same HTML-to-text reduction `record_claim` uses, before `check`.
     - The hook passes the subject and the body to `evaluate()` separately, and the subject/body split happens in `evaluate()` (component 3). The hook does no rule work of its own.
   - **Recipients:** to, cc and bcc together must be exactly one address. More than one blocks with `one recipient per gated draft`, because `presend_check` judges one contact at one company.
   - **Inputs it assembles:**
     - Claims from `<gates_home>/drafts/<domain>/<contact>/claims.json`. A missing file is not an error: it means an empty list. A draft with no numbers can pass, and any number fails `claims`.
     - `register` from the hook config. The default is `cold`.
     - `today` from the system clock, passed in explicitly and recorded in the verdict.
     - `sender_owner` and `max_unanswered` from the hook config.
   - **CRM source:** live at hook time, so the check sees replies or owner changes made since the draft was written.
     - With `crm.source: hubspot`, the hook:
       - builds `HubSpot(_token())` from the token variables the adapter already reads
       - loads the field mapping with `load_mapping()` from the `hubspot` section of `gates/hook.config.json`
       - calls `export(client, domain, mapping, contact)`, which returns `(crm, warnings)`
       - adds each warning, such as a missing owner or contact-block property, to the verdict as a WARN-level finding with rule `crm_coverage`, so you can see a check that silently ran on defaults.
     - With `crm.source: file`, it loads that path (the demo uses `demo/mock_crm.json`).
     - A missing token, a HubSpot error or a missing file blocks with the reason. It never falls back to a stale copy.
   - **Time budget:** Claude Code kills a hook that runs past its timeout and lets the tool call go ahead. So the hook must finish well inside that limit.
     - `hooks/hooks.json` sets `"timeout": 60` for the hook, and the hook enforces its own 40-second total budget.
     - One `export` makes about 10 HubSpot requests: 1 company search, 4 association lists, 4 batch reads and 1 contact search. In hook mode each request gets an 8-second timeout and at most 1 retry with a 1-second backoff. This needs two small, backwards-compatible additions: optional `timeout` and `max_retries` parameters on `urllib_transport` and `HubSpot`, with today's defaults unchanged.
     - The hook checks the budget before every request. When it runs out, the hook exits 2 with `CRM read exceeded the 40 s budget`.
     - **Hard deadline:** a per-request timeout doesn't cap the hook's total run time. It covers each socket operation, not DNS lookup, and not a `Retry-After` sleep. So the hook starts a watchdog at launch: a daemon `threading.Timer` that writes `gate deadline exceeded` to stderr and calls `os._exit(2)` at 45 s.
     - In hook mode, `HubSpot._call` ignores `Retry-After` and caps every backoff at 1 s. It checks the remaining budget before each sleep as well as before each request.
     - A test uses a transport that sleeps past the deadline, and another that returns `Retry-After: 30`, and asserts exit 2 before 60 s.
   - **Config:** the hook reads `${CLAUDE_PLUGIN_ROOT}/gates/hook.config.json` for its register and CRM settings. It then **forces `require_evidence` on**, whatever any config says, and loads the checker rules from that config.
   - **Fails closed:** the whole hook runs inside one `try`. Every error path ends in exit 2 with the reason: unparsable tool input, missing recipient, missing CRM data, a config error, or any uncaught exception. Claude Code treats other non-zero exits as non-blocking, so the hook never exits with anything else.
   - It never trusts a verdict the agent reports; it always re-runs `evaluate` itself.
6. **Plugin wiring:**
   - `.mcp.json` and `hooks/hooks.json` go at the repo root, which is the plugin root. Only `plugin.json` lives in `.claude-plugin/`.
   - Both reference scripts through `${CLAUDE_PLUGIN_ROOT}` and run with `python3`. Python 3.9 or newer is the one requirement on the user's machine, the same as the existing CLI.
   - One plugin install gives both the tools and the enforcement.

Later, on the same core: `python -m gates.serve` HTTP endpoint for a Clay HTTP API column, with an "only run if pass" condition on the send step.

## Open Questions

1. **Exact Gmail field names.** The tool names are known (`create_draft`, `update_draft`, `send_message`, `reply`, `forward`). The input field names for recipients, subject and body are confirmed in step 1, before the hook is written.
2. **Hook latency.** A live HubSpot read on every `create_draft` makes about 10 API calls, bounded by the 40-second budget. Measure the typical time during the demo. If it's routinely more than a few seconds, consider caching the company record for a short time. That would trade some freshness for speed, and it's a decision to make explicitly, not by default.
3. **Trust boundary.** The agent has local file access. In principle it could write a fake snapshot file, edit `gates/hook.config.json`, or edit the hook itself. The hook forcing `require_evidence` on closes the easiest config bypass, but not edits to plugin files. The design defends against an agent cutting corners, not a determined adversary. State this in the README rather than overclaim. A later option: keep the evidence store and hook config outside the agent's writable directories.
4. **Pages that block fetches or render with JavaScript.** These fail `record_claim`. The likely answer is to route them to the human queue (`docs/human-queue.md`) rather than allow a manual override.
5. **Quote matching.** Exact match after whitespace, case and quote-character normalisation, or a small tolerance? Start exact and see how often real pages fail.

## Success Criteria

- In Claude Code with the plugin installed, the four-step demo sequence works live, with the exact messages listed under What Makes This Cool.
- In Claude Code with the plugin installed, no Gmail connector call creates, changes or sends a draft while `evaluate` fails, even when the agent never calls the MCP tools. Tests cover each error path ending in exit 2:
  - malformed tool input
  - more than one recipient
  - missing CRM data
  - HubSpot error
  - CRM read exceeds the 40-second budget
  - internal exception
- A missing claims file is not an error. Tests show a draft with no numbers passes, and the same draft with a number fails `claims`.
- The MCP server and the hook resolve the same claims path (a test covers mixed-case and odd-character addresses).
- `record_claim` rejects `file://`, other non-http(s) schemes, redirects to them, and private addresses. Each has a test.
- `evaluate()` is deterministic: a test runs it twice on the same inputs, `today` included, and compares bytes.
- No new runtime dependencies. Tests run offline from committed HTML fixtures. CI stays green on 3.9 to 3.14.
- `python -m demo.run_demo` output is unchanged.
- A GIF of the sequence is in the README.

### R3-1 — consistency (blocking)

**Problem**

> The new subject/body split appears only in the hook section. Component 3 still says `evaluate` 'Runs `checker.check()` on the subject and body joined', and the hook 'always re-runs `evaluate` itself'. The two passages contradict each other. If the split lives in the hook, the MCP `evaluate` tool still joins the subject and body, so its advisory verdict differs from the hook's (the length rule counts subject words, and rhythm treats the subject as a sentence). If the split lives in `evaluate`, Component 3 is wrong. This is the R2-5 obligation, still unmet in `evaluate`.

**Remedy**

> Put the split in `evaluate()`: the full `check()` on the body, the named subset on the subject, and subject findings merged with a `subject:` prefix. Rewrite Component 3 to match, and have the hook section say it gets this from `evaluate` rather than doing it itself.

### R3-2 — completeness (blocking)

**Problem**

> Checking the 40 s budget only before each request does not bound the hook's run time, so the hook can still overrun the 60 s timeout and fail open. (1) `HubSpot._call` sleeps `_retry_after(resp_headers) or 2 ** attempt` (gates/hubspot.py:104-105). Adding `max_retries=1` keeps a 1 s backoff only when no Retry-After header comes back. A 429 with `Retry-After: 30` sleeps 30 s, and the budget is never checked during the sleep. (2) The `urlopen` timeout applies to each blocking socket operation, not to the whole request, and DNS lookup is not covered at all. So the '8-second timeout' is not a cap on one request. Worst case on the design's own numbers: a request that starts just before 40 s, plus 8 s, is about 48 s. But any Retry-After over about 12 s, or a slow-drip response, passes 60 s, and the draft is then created ungated.

**Remedy**

> Make the budget a hard deadline. Start a watchdog at hook start, either `signal.alarm` or a daemon `threading.Timer` that writes the reason and calls `os._exit(2)` at about 45 s. Also, in hook mode, cap or ignore Retry-After so every backoff is at most 1 s, and check the remaining budget before each sleep as well as before each request. Add a test where the transport sleeps or returns a large Retry-After, and assert exit 2 before the deadline.

### R3-3 — feasibility (minor)

**Problem**

> `HubSpot.__init__` already takes `retries: int = 4` (gates/hubspot.py:84-93), so adding `max_retries` would mean two parameters for one thing. `urllib_transport` has to keep the four-argument `Transport` signature (gates/hubspot.py:69, 102), so its timeout can't be passed per call. It has to be bound in advance.

**Remedy**

> Use the existing `retries=1`. Add `timeout` as a keyword-only argument on `urllib_transport`, bound with `functools.partial` (or a small factory), and leave the defaults unchanged.
